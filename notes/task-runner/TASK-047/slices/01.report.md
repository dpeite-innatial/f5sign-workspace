## Tests written
`tests/F5Sign/Foundation/Integration/EventStreamSubjectBoundaryTest.php` (`#[SkipDatabaseRollback]`), 7 cases:
- `it_stops_at_the_named_subjects_row_not_the_first_of_the_type` (AC-9a). It also asserts that the type-only read returns 2 rows.
- `no_row_of_that_type_and_subject_is_no_boundary` (AC-9b). The type list is `[RECIPIENT_SIGNED, ENVELOPE_COMPLETED, ENVELOPE_VOIDED]`. Y is the subject of a FILLER row, and every boundary-type row is about X.
- `a_writer_still_open_below_the_subject_boundary_makes_the_read_not_settled` (AC-9c). It reads twice: open writer → `StreamNotSettled`, and after the commit the writer's row is in the result.
- `a_repeated_row_of_the_type_and_subject_does_not_move_the_boundary` (AC-9d)
- `another_tenants_row_with_the_subject_reads_as_no_boundary` (AC-9). It first checks that the owner tenant reads Ok.
- `a_missing_subject_is_refused_by_the_function` (AC-9): SQLSTATE 22023
- `the_subject_read_is_owned_by_the_reader_and_executable_by_the_application_only` (AC-9): owner, acl, prosecdef, volatile, search_path

## Red reason seen
All 7 cases were written before any code and run together, one batch rather than one Integration test at a time. Every red was the slice's "absent" reason:
- 5 cases: `Call to undefined method DbalEventStreamReader::readSettledToSubject()`.
- 2 cases: `function platform.read_settled_stream(uuid, text[], uuid, integer) does not exist` (SQLSTATE 42883).

Each case's guard was then proven by the sabotages below, not by this red.

## Sabotage performed
Each sabotage changed the migration, then re-applied it on the lane test DB with `wt-backend-sf env=test admin=1 cmd="doctrine:migrations:execute … --down|--up -n"`. Restore and re-apply were done the same way, and the verify set was green afterwards.

1. **Subject filter dropped from the FIRST `min()` only (the slice's sabotage).** `it_stops_at_…` did **not** go red. `no_row_of_that_type_and_subject_is_no_boundary` went red with `LogicException: read_settled_stream returned no row`.
   - Why: the first lookup only decides `NO_BOUNDARY`. The real boundary comes from the second lookup after the wait, and that one still filtered on the subject.
   - The slice's expected red for this sabotage (AC-9a, 2 ≠ 4) is not what this guard produces. The first lookup's subject filter is pinned by AC-9b instead.
2. **Subject filter dropped from the SECOND `min()` only (added).** `it_stops_at_the_named_subjects_row_not_the_first_of_the_type` went red: the arrays were not identical (the type-only prefix came back).
3. **`min(` → `max(` in both lookups.** `a_repeated_row_of_the_type_and_subject_does_not_move_the_boundary` went red: it expected `[FILLER, RECIPIENT_SIGNED]` and got 4 rows.

The adapter refactor (closure-based `settle()`) came after the sabotages. It does not touch the SQL guards, and the verify set was re-run green after it.
