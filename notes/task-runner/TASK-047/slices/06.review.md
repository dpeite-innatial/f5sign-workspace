## Findings

### F1 (90, rule 1): the reused failure family and identity say "trail" for a receipt
The receipt adapter returns `GenerationMismatch` and `TrailNotEncodable`, so their messages and docblocks are
now false on half their paths. A receipt failure logs "The trail names Typst …" / "The trail has no JSON
form". The same is true of `TrailRenderFailure` ("An audit trail could not be rendered"; "`TrailRenderer`
returns a failure …"), of `TrailNotEncodable`'s `{@see TrailJson::encode()}`, of `RendererIdentity` ("What a
trail renderer is"; "A trail's `Generation`"; only `TrailRenderer::render()` is named), and of `TypstCommand`
("The command lines that run Typst for the audit trail"; `INPUT` "The trail JSON's file name").

Ruling on concern (1): **a slice-local fix is possible without changing trail behaviour or trail tests.**
`TypstTrailRendererTest` pins both messages exactly (`'The trail names Typst %s …'`, `'The trail has no JSON
form: %s'`), so keep those strings as the default.

Fix (the orchestrator adds the four exception/port files to *Files*, and allows a docblock-only edit of
`TypstCommand`):
- `GenerationMismatch::__construct(RendererIdentity $named, RendererIdentity $actual, string $document = 'trail')`
  with the message `'The %s names Typst %s and template %s; the renderer is Typst %s with template %s.'`.
  Do the same for `TrailNotEncodable::__construct(JsonException $previous, string $document = 'trail')`
  with the message `'The %s has no JSON form: %s'`. `TypstReceiptRenderer` passes `'receipt'` to both.
- Docblocks: `GenerationMismatch` "The document's generation (a trail's or a receipt's) …". In
  `TrailNotEncodable`, cite both `TrailJson::encode()` and `ReceiptJson::encode()`. In `TrailRenderFailure`,
  "An audit trail or a receipt could not be rendered", returned by both `TrailRenderer` and `ReceiptRenderer`.
  `RendererIdentity` gets "What a trail or receipt renderer is …", naming both `render()`s.
- `TypstCommand`, docblocks only, constants unchanged: "for the audit trail and the receipt". Its `INPUT`
  becomes "The document's JSON file name …; named `trail` for every document".
- In `TypstReceiptRendererTest::a_receipt_that_names_another_renderer_is_not_rendered`, add
  `assertStringStartsWith('The receipt names Typst', $failure->getMessage())`.

### F2 (85, check 1 / rule 4, security): the adapter's failure paths and security properties are unpinned
`TypstReceiptRendererTest` has no case for a missing or non-executable binary, an unreadable template, a
scratch dir that cannot hold a job, a timeout, a program that makes no PDF, a JSON-less receipt, the **empty
child environment** or the **0700 job directory**. The last two are security properties: the adapter's own
docblock claims them, and the job directory holds the recipient's personal data. The code is a copy, but
Infection treats `TypstReceiptRenderer` as its own file. Mutants in `run()`, `readTemplate()`, `compile()`
and `emptyEnvironment()` survive today.

Ruling on concern (2): **yes, warranted.** The fakes already exist in `tests/Fixtures/typst-fakes/`.

Fix: add these methods to `TypstReceiptRendererTest`, each a copy of the `TypstTrailRendererTest` method of
the matching name, run with `TypstReceiptRenderer` and `ReceiptFixtures::signer()` (named with the renderer's
identity), and each citing `@criterion TASK-047 V-2`:
- `a_renderer_that_cannot_run_is_unavailable`: the four cases plus the no-scratch case, from both calls.
  The template path in the message becomes `/nonexistent/receipt.typ`.
- `a_compile_past_its_time_limit_times_out`
- `a_program_that_makes_no_pdf_fails_with_what_it_said`: failing, killed, silent and garbled-version.
- `the_program_inherits_no_environment`
- `the_job_directory_is_private_to_this_user`
- `a_receipt_with_no_json_form_is_not_rendered`: rebuild the signer with a recipient name of
  `new Stated("\xB1", Source::ROW)`. Assert `TrailNotEncodable`, a `JsonException` previous, and (after F1)
  the message `'The receipt has no JSON form: …'`.

Add `#[UsesClass]` for `RendererUnavailable`, `RendererTimedOut`, `RendererFailed` and `TrailNotEncodable`.

### F3 (85, check 4, recipient-facing evidence wording): an approver's receipt reads "Firma" for their approval
In SEQUENTIAL_PADES an approval's fact is `RECIPIENT_SIGNED` (ADR-0086 §2.2; `ReceiptFixtures::approver()`
has `ReceiptFact('RECIPIENT_SIGNED', 8, …)` and that boundary). `receipt.typ` labels it
`RECIPIENT_SIGNED: "Firma de la parte"`. So the approver's page prints "Tipo: **Aprobación**", then "Hecho y
hora: Firma de la parte, hecho nº 8", then "Hecho que cierra la actuación — Tipo: Firma de la parte". Under
*Limitaciones* the same page says "Una aprobación no añade una firma al documento." The recipient's own
evidence document contradicts itself. Separately, "la parte" is the trail's term, while every line of the
receipt says "destinatario".

Ruling on concern (3): copying the labels verbatim from `trail.typ` is wrong for this document.

Fix, in `receipt.typ` only (the trail stays unchanged):
- In the `event-type` group set `RECIPIENT_SIGNED: "Actuación del destinatario registrada (firma o
  aprobación)"`, `SESSION_DECLINED: "Rechazo confirmado por el destinatario"` and keep the others.
- Also print the act's fact in "Hecho y hora" with the act-kind label: replace `fact(act.fact)` with
  `[#lbl("act-kind", act.kind), hecho nº #str(act.fact.position) del registro, #when(act.fact.at)]`.
- Keep the label set's keys as they are: `the_template_labels_every_code_the_receipt_owns` is unaffected,
  and the identity and wiring tests hash the file from disk.

### F4 (rule 1/2, no cut): the adapter's class docblock contradicts its own `remove()`
The class docblock says "in a private job directory removed before it returns". `remove()` in the same file
says "A directory that cannot be removed is left behind". The trail's docblock stated both exits (a failed
removal, a killed worker) and `BL-321`; the receipt's copy dropped them, and the slice's *Prose to write* was
shorter than the code.

Fix: append to the class docblock "A removal that fails, or a worker killed during the call, leaves it
behind; nothing removes it yet ([`BL-321`](../../../../../docs/BACKLOG.md))." Also restore "which only this
process's user can read" after "inside the job directory" in **Security**, since the code makes it `0o700`.
