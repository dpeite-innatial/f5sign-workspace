## Low confidence

- **Collision risk of the fixed Factor5 pair (confidence 65).** The registry id is
  `IssuedReceiptId::fromEnvelopeAndRecipient(F5::ENVELOPE_ID, F5::CONSIGNOR)`, so it is the same on every run. The
  primary key is global, while RLS scopes reads by tenant. If a row with that id survives under an earlier run's
  tenant, the next run fails like this:
  1. The step-1 `exists()` check runs under the new tenant, sees nothing, and both issuances proceed.
  2. Both `ON CONFLICT (id) DO NOTHING` claims lose against the invisible row.
  3. Both custodies are withdrawn.
  4. `find()` returns null, and the test goes red at `no receipt row stands`.

  That red repeats on every run until someone deletes the row by hand, and RLS hides the cause.
  - **Within one run:** no other committing test uses this pair today. A grep of the `SkipDatabaseRollback` tests
    found only `ConcurrentReceiptClaimTest`, which uses per-run v7 ids. PHPUnit runs serially, so nothing
    collides inside a run.
  - **Across runs:** a row survives only if the process dies before `tearDown()`. Examples are an Infection
    mutant killed on timeout (the class `#[CoversClass]` the use case, so Infection runs it) or a killed lane
    container. The lane DB persists for the whole task.
  - **Fix:** in `setUp()` and `tearDown()`, delete by id rather than only by tenant, through the owner connection:
    `DELETE FROM evidence_audit.issued_receipt WHERE id = :id`, with the id from
    `IssuedReceiptId::fromEnvelopeAndRecipient(...)`. Alternatively, a stray row could be made to fail with a
    message naming it.
- **The winner-side assertions (lines 209–215) are not reached by any sabotage of the use case either.** They hold
  on Storage's commit path and on which sealer's bytes went where, so they are a fixture check that tells first
  from second. That is acceptable as written (confidence 30).
