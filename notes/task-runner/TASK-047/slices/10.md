# Slice 10 — Two issuances of one receipt leave one row and one custody standing

| Tier | critical |
| Covers | AC-10b (through the use case) |
| Depends on | slice 08 |

## Goal
An Integration test drives two issuances of the same receipt through `IssueReceiptUseCase` against the real
registry and the real custody store, interleaved so the second completes while the first is between its seal and
its claim, and proves: one registry row, naming the second issuance's custody; the first's custody withdrawn and
its bytes undone; the first issuance ends without throwing.

## Why
"two issuances of one receipt on two connections, driven through the use case and not only the repository claim
(`ConcurrentTrailClaimTest` covers the claim alone): one row, one custody standing, the loser's custody withdrawn."
(§5, Notes on AC-10b)

## Decided here (why the interleaving and not two live connections in the use case)
The use case holds no transaction while it seals (ADR-0076 §2.6), so a second issuance that runs to its commit
inside the first's seal reproduces the race at the only point where it matters: the claim. The two-connection
property of the claim itself — a second claim **waits** on the first's uncommitted key — is
`ConcurrentReceiptClaimTest` (slice 07). Together they cover AC-10b; this slice records that split in the test's
docblock.

## Files
- Create `tests/F5Sign/EvidenceAudit/Integration/ConcurrentReceiptIssuanceTest.php`
  (`#[SkipDatabaseRollback]`, `#[CoversClass(IssueReceiptUseCase::class)]`, `#[Group('eIDAS-evidence')]`,
  `use OpensIdentityAdminConnection; use RemovesIssuedTrails;`).
- Do not touch: `src/`.

## How (decided here)
- Build two `IssueReceiptUseCase` instances by hand with the container's `DbalIssuedReceiptRepository`,
  `CustodyStore`, `UnitOfWork`, `ReceiptAssembler`, `Clock`; `TrailPortsFake::receiptSources()` and
  `envelopeReader()` for the reads (a SEQUENTIAL_PADES signer whose revision bytes the fake holds);
  `ScriptedReceiptRenderer`; a `ScriptedPdfSealer` for each. The first sealer's `during` runs the second use case
  to completion on the same command.
- The tenant is minted per run; the registry row and both custodies commit for real. `tearDown()` removes the
  tenant's receipt rows (`removeIssuedTrailsOf`) and, as `IssueAuditTrailPhaseBoundaryTest` does, whatever custody
  rows the run left.
- Assert: `find(id)` names the second custody; `CustodyStore::describe(first custody)` reports it withdrawn (read the
  state through Storage's contract — whatever `describe()` exposes for a withdrawn custody) and holds no bytes;
  `describe(second)` is present with the second's digest; the first `execute()` returned normally.
