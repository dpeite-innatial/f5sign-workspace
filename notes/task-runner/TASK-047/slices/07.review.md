## Verdict
The code is a faithful mirror of the trail registry. Diffing `DbalIssuedTrailRepository`, `IssuedTrailId`,
`AuditedEnvelopeRef` and `InMemoryIssuedTrailRepository` against their receipt twins, with Trail replaced by Receipt,
leaves only the second key column, the boundary rename and the slice's prose. The migration matches the slice's table
exactly: the columns, the four named constraints, ENABLE and FORCE, the policy with USING and WITH CHECK, the
tenant-stamp trigger, `SELECT, INSERT` plus the column-scoped `UPDATE`, no DEFAULT and no FK, and `down()` revokes
before it drops. It does not grant schema USAGE again, because `issued_trail`'s migration already granted it, and that
is correct. I recomputed the two pinned v5 ids in `IssuedReceiptIdTest` independently with Python's `uuid.uuid5`, and
both match. The sabotage reds match the slice's *Guard that must fire* for both rows: a 23505 unique violation for the
missing `ON CONFLICT`, and "row-level security is not forced" for the missing FORCE. All criteria the slice covers
(AC-10, AC-10b, AC-12, AC-13) have citing tests that assert the stated behaviour. `SchemaConformanceTest` needed no
exemption, because the table carries only the canonical policy. Slice 12 adds the custodian policy, and that slice will
need a `NON_CANONICAL_POLICY_TABLES` entry.

  therefore a decision, not a bug (authoring rule 3).

  rule forces it. I ran `rg` over src, tests, docs, config and var/task-runner/TASK-047. No later slice file names
  `IssuedReceiptId::forRecipient`. The only hit is slice 07 itself, which is historical. The other `forRecipient` hits
