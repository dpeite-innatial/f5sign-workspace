# security-audit-backend — TASK-067

**Status:** WARN
**Issues:** 0 blocking, 7 warnings (read-only static audit: no tests, no docker, no network; CVE status of the pinned wheels NOT checked).

## Blocking
None.

## What was checked and held
- **Injection / argv.** `PyHankoFormEngine.php:337` builds `new Process(array, null, env, $input, timeout)`: an argv list, no shell string. `PyHankoCommand.php` gives only `[python, script, 'inspect'|'apply', '--memory-limit-bytes', (string) int]`, all fixed parameters (`config/packages/signature_execution.yaml`). The script re-validates argv strictly (`form_engine.py:84-92`). No value or PDF is on the command line; both travel on stdin (`form_engine.py:97`).
- **Environment.** `PyHankoFormEngine.php:108` names every `getenv()` and `$_ENV` key as `false`, so the child gets an empty environment (DB credentials, `APP_SECRET`, `SESSION_CREDENTIAL_SECRET` do not reach it). Interpreter is an absolute path, so the empty `PATH` is harmless.
- **Error leakage.** `form_engine.py:33` redirects Python's `sys.stderr` to devnull, and the PHP side never calls `getErrorOutput()`. Failures are exit code plus `FormEngineFailure` enum (`PyHankoFormEngine.php:339-357`). `FormEngineFailedException` carries kind, exit and check only, no `previous`. It extends native `\DomainException`, not the kernel one, so `ApiExceptionListener::domainFailureStatus` returns null and it takes the generic 500 path with no detail.
- **Log PII.** `PsrFieldDrawingLog.php` logs ids, reason, enum name and exit code only. No value reaches the logger.
- **Content-stream injection.** `form_engine.py:490-492` escapes `\ ( )` and encodes to cp1252, so a value cannot leave its string literal. Field names reject `.` (`a_name`). Names, kinds and rotations are whitelisted.
- **Output not trusted.** `DrawnRevisionCheck::verify` requires the output to begin with the input bytes, to be longer, to carry the filled values, and to carry the signature fields with the requested locks. A tampering engine cannot rewrite earlier bytes.
- **fieldId into DSS.** `DocumentSigner.php:165` sends `$fieldIds[$k]`. These are `f5s_sig_<random_bytes(8) hex>` made in `FormRevisionPlanner::signatureName()`, never client input. `DssPayloadMapper` only forwards them; the `imageParameters` fallback (diff lines ~3663-3750) is correct. No injection.
- **Tenant isolation.** The diff has no migration, no table, no route and no auth change. Planner input is the act's `EnvelopeContextView`; field names are `f5s_<fieldId UUID>`; the custody is opened with `$context->tenantId` (`DocumentSigner.php:184-189`). No cross-tenant surface. A cross-tenant test is not applicable because no tenant-scoped read or route was added.
- **Supply chain.** `pyhanko-requirements.txt` pins every package by version and SHA-256, installed with `--require-hashes --only-binary=:all:` (`Dockerfile` pyhanko stage), so there is no sdist and no build step. The venv is root-owned and not writable at runtime (it is only COPYed), and a version assert runs at build time and again at runtime (`VERSION_MISMATCH`).
- **Secrets.** Nothing committed. The five parameters are non-secret fixed values.

## Warnings
1. **[pii-in-trace / BL-278] The `#[\SensitiveParameter]` coverage is a hand-listed set.** `FormEngineSensitiveParametersTest::parameters()` enumerates 22 parameters. `PyHankoFormEngine::fields/fill/run/inspect/apply`, `DrawnRevisionCheck::verify`, `DocumentSigner::sign/seal/apply/formOf` and `FieldTextLayout::layOut` are covered; I found no parameter that carries a string or array value left out. Objects (`FormState`, `DocumentView`, `$marks`) appear in a trace as `Object(Class)`, so they are not a leak. But the test lists names and cannot see a new one: a future string or array parameter carrying a value (for example `labelOf(FieldView, string $value)` at `FormRevisionPlanner.php`, which cannot throw today) will not be caught. Prefer a census plus fail-on-unclassified. Also `FieldFill`, `AppearanceLine` and `DrawnRevision` constructors carry values but cannot throw, so they are safe now. Locals such as `$bytes` and `$text` are not captured by traces. Whether `zend.exception_ignore_args` is on in the image was not verified.
2. **[dos] Resource limits are partial.** The child sets `RLIMIT_AS` (768 MB, `form_engine.py:591`) and PHP applies a 20 s timeout. There is no `RLIMIT_CPU`, `RLIMIT_NPROC` or `RLIMIT_NOFILE`. Each concurrent signing act can hold 768 MB, so N php-fpm or worker slots can commit N times that, a sizing question for infra. The PHP side holds the PDF 3+ times in memory (raw, base64, JSON, then the response); a PHP `memory_limit` fatal is not handled. I did not find the maximum upload size in this diff (unverified).
3. **[dos / availability] A hostile or very large PDF makes the document unsignable and the envelope stuck.** `DocumentSigner::formOf` treats only `PDF_UNREADABLE` as "sign without drawing". `MEMORY_LIMIT`, `TIMED_OUT` and `KILLED` are rethrown and fail the act on every retry. Example: `page_tree` (`form_engine.py:218-234`) keeps `seen` per path, not globally, so a DAG of shared `/Kids` expands exponentially until memory or the timeout stops it. The attacker is the tenant's own uploader, so this is self-inflicted, but it also blocks the company seal. Consider a global visited set in `page_tree`, and decide explicitly (ADR-0085 §2.6) whether a deterministic `MEMORY_LIMIT` on `inspect` should degrade like `PDF_UNREADABLE`.
4. **[hardening] The interpreter is not started isolated.** `PyHankoCommand::command` omits `-I` (or `-E -s`). The empty environment already removes `PYTHON*`, but `sys.path[0]` is the script directory (`assets/signature-execution/`), so a stdlib-named file added there would shadow it. Cheap to add `-I`.
5. **[hardening] No privilege or network sandbox.** The child runs with the php-fpm user's privileges and network. The script only reads and writes (no validation), so pyHanko makes no OCSP or CRL fetch; I saw no network path. A seccomp or no-network profile is not available here. Report as residual, not a defect.
6. **[supply-chain] Residual points.** (a) The `FROM php:8.5-fpm-alpine` tag is not digest-pinned, and neither is `apk add python3` in pyhanko, dev and runtime. These are separate installs, so a drift of the python minor version between stages would break the venv (`lib/python3.14`) at runtime, not at build. (b) The venv's own `pip` and `setuptools` are unpinned and `pip` stays in the runtime image. (c) The unused transitive packages (`requests`, `urllib3`, `certifi`, `lxml`, `pyyaml`, `oscrypto`) widen the CVE surface for a drawer that needs only `pyhanko.pdf_utils`. (d) No SCA or CVE scan of the 18 pinned wheels was run; hashes prove integrity, not safety. The versions are later than my knowledge, so treat them as unverified.
7. **[pii-at-rest] More PII is now drawn and recorded earlier.** `Recipient::recordAdmittedReservations` writes the reservations text in the clear to the existing column at admission rather than at completion (a commit that never completes now keeps it; ADR-0069 §3.2, ADR-0033 still Proposed, FieldCipher has no callers). Field values are also drawn into the stored PDF, which is the feature. No new column, so no new BACKLOG row is strictly needed, but the earlier-write window should be named in ADR-0085 or BL rows. In addition, a PDF uploaded with decoy `f5s_*` fields makes `isPrepared()` true, skips field creation, and the fill then fails with exit 5. That is a self-DoS by the tenant, not a leak.

## Notes
- `json.loads` in the script accepts NaN and Infinity, which would produce a corrupt content stream (`fmt`, `numbers`). Input comes only from PHP layout code, so it is low risk.
- `FormEngineFailedException` is not a kernel `DomainException`, so it maps to 500 by design; that avoids leaking and is consistent with "a replay can still draw".
