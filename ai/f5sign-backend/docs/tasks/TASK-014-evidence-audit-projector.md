## 1. Why this task exists

The event log is now the system of record. Its whole *raison d'être* was this: **Evidence & Audit as a projection over the log** (that was the reframe TASK-009 drove). The substrate is landed and green — this is the payoff. E&A owns *projections*, not a store; the log is the source of truth, the WORM-sealed evidence artifact is the legal source of truth per envelope, and everything else is a rebuildable read model.

Two facts set the starting shape:

1. **The BC is greenfield.** The stage-1b sunset deleted every E&A file (`AuditCommandInterface`, `InMemoryAuditCommandAdapter`, the fakes — the sync `record()` path). `src/F5Sign/EvidenceAudit/` and `tests/F5Sign/EvidenceAudit/` do not exist. There is no implemented model pinning the design down.

2. **The domain model needs fleshing out — this is in scope (the user's explicit steer).** The design-repo `04 - Evidence and Audit BC.md` predates the log-as-system-of-record reframe entirely (no banner; its whole tactical persistence model — write-time chain + `SELECT…FOR UPDATE`, the removed `record()` port, the three-store sync/async routing — is stale). The backend `docs/ddd/evidence-audit-domain-model.md` has a reframe banner but its *body* still presents the removed `AuditCommandInterface`/`InMemoryAuditCommandAdapter` as realized. So we are not building a projector against a settled model — **we develop the E&A domain model as the first act of this work** (§6 Stage 0), UL-first, and the projector *realizes* it.

## 2. Where we start from (ground truth, verified on `master`)

- ⚑ **The per-recipient signing facts are not yet in this task's inventory** *(added 2026-07-28)*. [TASK-017](TASK-017-sequential-incremental-pades.md) §6 and [ADR-0034](../adr/ADR-0034-sequential-incremental-pades.md) both assert that **the Evidence & Audit projector is the consumer of `DocumentSigned`** — a cross-BC consumption obligation stated in the *producer's* docs that never landed here. Under `SEQUENTIAL_PADES` each recipient's act produces its own `DocumentSigned` (plus the `SigningAssignment` model that scopes which documents a recipient signs), so the evidence surface is **per recipient per document**, not one seal event per envelope. Anything in §4 that assumes a single terminal signing fact per envelope needs checking against that. This bullet records the gap; the inventory work itself belongs to the Stage-0 flesh-out.

- **Log read-contract** (`Foundation/EventLog/`, migration `Version20260713000004`): columns `sys_global_position` (gappy IDENTITY, order-only), `sys_transaction_id` (xid8, watermark), `stream_id` (the envelope), `subject_id` (the aggregate a fact is about), `event_type`, `schema_version`, `payload` (BYTEA canonical JSON), `tenant_id`, `actor_kind`/`actor`, `occurred_at`/`sys_recorded_at`, `sys_commitment` (keyless SHA-256 leaf, scheme-versioned). `EventRelay.relayBatch` reads `WHERE (sys_transaction_id, sys_global_position) > cursor AND sys_transaction_id < pg_snapshot_xmin(...)` ORDER BY the composite — the gap-safe watermark. Checkpoint is **per-consumer** (`event_checkpoint` PK=consumer; `EventRelay` already parameterises `$consumer`), so a second consumer is isolated by construction.
- **The app role cannot read the log.** `f5sign_app` has EXECUTE on `platform.append_event()` and *nothing* on the table — no SELECT. The only provisioned reader is BYPASSRLS `f5sign_relay`. A projector needs its own read grant (§4.2).
- **WORM is realized** (ADR-0016 Stage-2): `Foundation/Storage/{ObjectStore,S3ObjectStore,StorageZone}` + async-aws/s3, bucket-default Object-Lock COMPLIANCE on the WORM zones. **Deferred there:** per-object retention/legal-hold, the compliance-class→profile domain model (matters for §5.5).
- **The SE seal seam is thin, not empty.** SE has `DssClientInterface` + `DssHttpAdapter` (EU-DSS HTTP), `DocumentSigner` (named `DocumentSealer` when this was written; renamed by [ADR-0034](../adr/ADR-0034-sequential-incremental-pades.md) Decision 5 — see §7 #1), `SignatureLevel` — a *PAdES document* signing path. What's missing is **XAdES-B-LTA signing of the audit-trail XML** — an *extension* of an existing DSS integration, not a greenfield signer.
- **Kernel:** `ActivityLogEntry` (pure marker, non-transition observations) and `AuditableEvent` (its `payload()` is the deferred-reduction target) live on the `Event` floor. `EventLogCommitment` (the PHP twin that recomputes `sys_commitment`) exists and is currently unused by anything downstream.

## 3. The architecture — **C′: structural Evidence≠Audit, fold-at-seal**

Chosen by a 3-architecture judge panel (C won objective-coverage + domain-fidelity; A won ground-fit/simplicity). C′ is the synthesis: **take C's structural two-consumer split, graft A's fold-at-seal minimalism (no long-lived per-envelope chain state) and honest staging, and B's per-entry PII classification.**

Two independent log-polled BYPASSRLS consumers over the one `platform.event_log`:

- **`ea_activity` — this IS Audit.** An always-on tail materialising a complete forensic view of *all* facts (legally-material transitions **and** `ActivityLogEntry` observations: abandoned session-starts, failed/declined auth) from **raw stored columns + codec-decoded payload, without rehydrating the PHP event** — which sidesteps the `DomainEvent`-only `EventTypeRegistry` that would otherwise dead-letter the non-`DomainEvent` facts. Rebuildable (truncate + reset checkpoint + replay = byte-identical). Carries **no chain of its own** — tamper-evidence is the per-row `sys_commitment` leaf + immutability; the strong anchor for material acts is the sealed Evidence artifact.
- **`evidence_seal` — this IS Evidence.** A completion-triggered assembler: find `EnvelopeCompleted` facts not yet sealed → reconcile completeness fail-closed → fold the tamper chain in one pass → assemble the curated `AuditTrailXML` (chain **inside** the artifact, `EvidencePacket` references embedded) → XAdES-B-LTA seal to WORM → append the seal fact back to the log.

The distinction is *structural*, not implicit: different lifecycles (continuous tail vs completion batch), storage (rebuildable read model vs WORM artifact), and privacy postures (lean pseudonymous rows vs curated plaintext-in-WORM). Collapsing them forces one compromise on both.

## 4. The design (grounded)

### 4.1 Projections
- **`ea.activity_projection`** — rebuildable table, PK = log `id`. Columns projected straight from stored form (stream_id, subject_id, event_type, actor, occurred_at, sys_recorded_at, sys_global_position, tenant_id, `emitting_context` derived from the `App.<BC>.Event.<Name>` naming, + a canonical-JSON view of the lean payload). Never a source of truth.
- **`AuditTrailXML`** — the WORM Evidence artifact, the single legal source of truth per envelope (EVI-2). Chain lives inside it; PDF is a derived on-demand render, never persisted.
- **`ea.sealed_trail_registry`** — rebuildable index (stream_id PK → WORM key, chain root hash, sealed_at, last_preserved_at). **Not** an idempotency source of truth (see §5.4).
- **`EvidencePacket` references** — per `signatureExecutionId`, the set of *references* to forensic captures (AUTH/DEVICE/GEO/UA in MVP; BIOMETRIC v2), chain-of-custody by reference, per-entry `piiClassification`. Slice-1: embedded into the artifact; a standalone queryable projection is v2 (§7).

### 4.2 Projector mechanism — **log-polled, dedicated role**
Both consumers poll; a broker signal is only ever a latency "poll-now" nudge that can be lost without affecting correctness (honours "wake-up must never become a durable handoff"). Sealing triggers on a *legally-material* completion fact — making the bus its trigger would turn delivery into a durability dependency and resurrect the dissolved ingest-consumer. Provision a dedicated **`f5sign_ea_projector`** BYPASSRLS role (SELECT on `event_log`, CRUD on its own `event_checkpoint`/`event_dead_letter` rows + `ea.*`) so E&A independence (IND-2) is structural at the DB-role level. Extract `EventRelay`'s watermark-tail read + per-consumer checkpoint UPSERT + dead-letter policy + codec seam into a reusable **`LogReader`** on that connection; the per-row action is "project/fold" instead of "dispatch to bus."

### 4.3 Chain — **projection-time fold, no chain table**
Deterministic fold at completion, living **inside** the sealed XML: read the reconciled stream ordered by `(sys_transaction_id, sys_global_position)`, assign dense sequence 0..N, `hash_n = SHA256(envelopeId ‖ sequence ‖ eventType ‖ detail ‖ hashPrev)` with `detail` = the stored `sys_commitment` leaf (**verified** to cover the wire payload bytes, exclude `sys_global_position`, and exclude the un-anchored `AuditableEvent::payload()`). No mutable tip, no `FOR UPDATE`, no serialization point. Deterministic + rebuildable (byte-identical root on replay); the chain layer supplies reorder-detection the leaf alone cannot. `verify()` re-folds.

> **Superseded 2026-09-21 for the audit trail:** the chain is `sha256-chain/1`, specified on [`Chain::over()`](../../src/F5Sign/EvidenceAudit/Domain/Trail/Chain.php). It orders by `sys_global_position` alone, because transaction ids do not survive a restore into a fresh cluster, and each link hashes the position and the commitment, not a dense sequence or the event type, which the commitment already covers.

### 4.4 Seal handoff
Assemble XML → **extend SE's `DssClientInterface` for XAdES-B-LTA** (E&A specifies the B-LTA profile; SE/EU-DSS applies the crypto/TSA — BND-1) → `ObjectStore` PUT to the realized `audit-trails` WORM zone → record pointer/root in the registry → append the seal fact back to the log (uniform recursion). Preservation tail (LIF-2): SE re-timestamps B-LTA, E&A schedules the scan and re-projects.

### 4.5 PII — Path B (MVP)
Log stays lean/pseudonymous (refs + the `sys_commitment` hash); plaintext PII lives only in the WORM artifact, pulled from producers via ACL read ports **at seal** (claim-check). The three redaction guards from TASK-009 §9 are load-bearing and carried verbatim in spirit: (1) type-enforced construction, (2) asymmetric serialization (assembler reads only `sys_commitment`-anchored stored bytes, never the redacted wire form), (3) completeness at the append chokepoint (Stage 5). Erasure = hash-then-erase (general) / crypto-shred (biometric, v2). **The non-biometric-plaintext-in-WORM residual is NOT safely deferrable — see §5.5.** **⚑ Target = Path A under C (confirmed 2026-07-06):** captures become ciphered log facts (per-envelope-DEK, crypto-shreddable — *per-subject* was the 2026-07-06 wording, superseded by ADR-0032 decision 3); the three-surface tiering (appearance / vectors / metadata) is in `docs/ddd/evidence-audit-domain-model.md` § *PII tiering and erasure*. Path B is the MVP interim.

### 4.6 Activity view
The Audit half; see §3. A shippable real-time forensic surface on its own at Stage 1, independent of the seal path.

### 4.7 `AuditableEvent` reduction (deferred → Stage 5) — retire both methods + re-seat as an orthogonal marker

*(Shape pinned by the 2026-07-06 kernel-taxonomy walk.)* Two of `AuditableEvent`'s three current commitments are mis-placed:

- **`payload()` is an integrity hazard.** The chain folds over `sys_commitment`-anchored bytes, which **provably do not include `payload()`** — folding over it would bind un-anchored data. The evidence snapshot **is** the anchored stored bytes; `payload()` retires.
- **`emittingContext()` is on the wrong axis.** "Which BC emitted this fact" is orthogonal to *both* materiality *and* transition-ness (every fact — transition or observation, material or not — has exactly one emitter), so it belongs on neither `AuditableEvent` nor `DomainEvent`. It is also **identity-constituting** (the `(emittingContext, type)` pair) and — like `eventType` — must be a **stable, declared value, never class/namespace-derived** (a BC rename must not rewrite recorded attribution; and `type` alone can't determine the BC, since the same `type` collides across BCs — `Document*` in Envelope vs SE).

**Resolution — one coherent move:**
1. **Retire `payload()`** (evidence shape = the `sys_commitment`-anchored bytes).
2. **Retire `emittingContext()` from the interface** — the `LegallyMaterialEventCatalog` attributes the BC **once per BC at registration** (`RegisterLegallyMaterialEventsPass` tags each BC's events with that BC's `BoundedContextId`; no central enum, no per-event restatement). The log's `emitting_context` column stays derived at append (§4.1); the catalog is canonical.
3. With both methods gone, `AuditableEvent` is a **zero-method marker** → **re-seat it as an *orthogonal* marker** (sibling to `DomainEvent`/`ActivityLogEntry`, implemented *alongside* either), **not** `extends DomainEvent`. This decouples "legally-material" from "is a state transition" and **closes the material-observation coverage gap structurally**: a legally-material *observation* — auth-lockout / brute-force proof, signer-disclosure-shown proof-of-presentation (§6) — becomes `implements ActivityLogEntry, AuditableEvent`, which the current linear hierarchy cannot express.

Sequenced last for kernel/producer blast radius (own green sub-stages); its **read-only classification half is pulled forward** (§5.2). **Interim:** the current AuditableEvents keep `emittingContext()`/`payload()` — no churn before the catalog exists; the Stage-5 sweep retires them fleet-wide.

## 5. Blocking corrections from the adversarial pass (folded into the design)

Seven objective-family verifiers ran against the synthesis. Five found `must_fix_before_build` holes; they are folded in here (not left as afterthoughts).

### 5.1 IND — the in-flight tamper window
`sys_commitment` is a **keyless** SHA-256 leaf (anyone who can write the table recomputes it); row-immutability is **grant-based** (binds the app, not a superuser/DBA/insider). Fold-at-seal faithfully seals whatever the rows contain — and TSA anchors the artifact's *existence-time*, not the *truth* of its contents. So an insider who alters a signed recipient's row during the multi-day in-flight window, recomputes its keyless leaf, then lets completion seal the forged stream, produces a permanently valid-looking trail no third party can detect. **Fix (in scope):** an **external anchoring of the *live* log** owned by E&A — the always-on `ea_activity` consumer periodically folds the log tail into a Merkle root and TSA-timestamps / externally witnesses it, so pre-seal tamper becomes third-party-detectable independent of completion; **bound and state the max unanchored window**; mandate the assembler re-verify every ACL-pulled plaintext detail against the row's `sys_commitment` before embedding; consider HMAC-keying the commitment (HSM-held) as a cheaper partial mitigation. (CT/Trillian/QLDB are the grounding-to-investigate.)

### 5.2 INT — the classification-sequencing contradiction
The fold (Stage 2) and the completeness reconcile (Stage 3) both need an event_type→legally-material classification — but the `LegallyMaterialEventCatalog` was sequenced at Stage 5, *after* the first real seals. **Fix:** pull the **read-only** classification half forward to Stage 0/2 (it has no blast radius; only the append-time *guard* and the `payload()` retirement need stay at Stage 5). Interim rule: any stream sealed before the catalog exists folds the **full stream superset** (integrity-safe), never an undefined "material subset." Also: an `occurred_at` monotonicity violation against the composite order **fails closed**, not just "cross-checks."

### 5.3 EVI — don't mint an unsealed artifact in irreversible WORM
The synthesis wrote *unsealed* XML to COMPLIANCE-5y WORM at Stage 3 and used `AuditTrailGenerated` as the seal-once key — so an envelope completed in the Stage-3→4 window gets a permanently unsealed, non-admissible artifact the logic then refuses to re-seal, and any later seal is a *second* immutable object (breaks EVI-2 "exactly one"). **Fix:** Stage 3 writes the unsealed XML to a **non-WORM / GOVERNANCE (deletable) staging** location; only Stage 4 PUTs the sealed artifact to COMPLIANCE. Split the marker: `AuditTrailAssembled` (Stage 3, not a commit key) vs `AuditTrailSealed` (Stage 4, the idempotency key); Stage 4 backfills every Assembled-but-not-Sealed envelope. Also **consent** (EVI-3, COV-2 — non-v2) is absent from the design: `CONSENT_RECORDED` must be a legally-material fact folded into the chain and narrated in the XML, with a pre-seal completeness assertion.

### 5.4 LIF — the non-atomic seal double-mint
The seal is a 3-step sequence across three systems with two disagreeing idempotency keys; a crash between the WORM PUT and the fact-append either never-seals-forever or double-mints two immutable, possibly-divergent artifacts. **Fix:** make the **log fact the sole commit token**; deterministic WORM key `= f(stream_id)` with write-once / `If-None-Match` so a retry re-attaches to the existing object; carry the WORM object id *inside* the seal fact; the registry is a rebuildable index, never a commit key; add a crash-between-PUT-and-append test. Plus a monitored per-artifact preservation deadline (LIF-2 fail-closed) and reconcile WORM retention to the legal obligation (LIF-1).

### 5.5 PRI — non-biometric plaintext PII in irreversible WORM (**non-deferrable**)
`must_fix_before_build=false` on the verifier, but the *decision* is non-deferrable: COMPLIANCE-mode WORM is irreversible, so the instant Stage 3/4 seals its first real envelope it mints a 5-year-locked plaintext-PII artifact with **no Art.17 erasure path** — and no later slice can retrofit encryption/crypto-shred onto already-sealed COMPLIANCE objects. Crypto-shred closes only the biometric class. This must be decided **before Stage 3 seals anything** — see §7. (It intersects ADR-0016's deferred per-object retention/legal-hold.) **⚑ 2026-07-06 (C confirmed):** the residual is now tiered — appearance PNG (ordinary, embedded in the *contract*, not the artifact), biometric vectors (ZK/custodian), metadata (ciphered log facts, crypto-shred); primary footing = Art.17(3) legal-basis retention (§7 #2a, incumbent-supported). See `docs/ddd/evidence-audit-domain-model.md` § *PII tiering and erasure*.

*(Two non-blocking verifier notes folded as constraints: COV-1 — **re-grounded by §7 #1**: there is no ACL-port set to enumerate; completeness is the **send-time roster (INV-B)** reconciled against the single envelope stream, with **INV-A** structurally guaranteeing every legally-material fact is *in* that stream. BND — pin edge ownerships: PDF/PAdES embedding is SE-mechanics, `AuditTrailPreserved` is emitted by SE's worker, biometric key-destruction goes through a custodian port, and — for the surviving PII-detail pull only — E&A reads producer detail via ACL ports, never models a producer's flow.)*

- **Stage 6 [v2] — EvidencePacket curation + biometric/crypto-shred + verify endpoint + read-side authz + live-log Merkle anchoring** (§5.1's external anchor may pull earlier — see §7).
