## 1. The model (locked in design discussion 2026-07-08)

**D1 — whose key signs each act → server-sign-as-signer (MVP).** The company/platform key (existing EU-DSS keystore alias) signs once per recipient, each incremental over the prior state, each with an optional per-recipient visible field + that recipient's captured evidence. **Reuses the existing DSS byte-path verbatim** (feed the tip bytes + a `SignatureImage` back through `DssClientInterface::seal` → an enveloped PAdES incremental update that preserves prior signatures) — **verified empirically against the running `eu-dss`, see §5**. Legally AES-class (identity from auth/evidence, as `SINGLE_SEAL` today); the crypto proves *chain ordering + integrity*, not personal-key possession. Reversible to real per-party certs (Cloud Signing §D.3, the `user_certificate` lifecycle) on the same artifact-chain substrate — deferred (§4).

**D2 + D3 — completion model / async → sign-then-complete, mode-gated, async.** In `SEQUENTIAL_PADES`, recipient-completion (which gates step activation) triggers on the **SIGN artifact landing**, not on consent being recorded. So the next step can't activate until the current signer's incremental PAdES is embedded as the tip → signer *k+1* sees *k*'s signature when they sign (**live visual accumulation**) *and* the crypto runs off the request path (**async**). This maps exactly onto the **two completion paths already in the code**:

| Mode | Completion driven by | SE / SIGN |
|------|----------------------|-----------|
| `SINGLE_SEAL` (today) | `SessionCompleted` → `OnSessionCompleted` | none (one company seal at close) |
| `SEQUENTIAL_PADES` | `RecipientSigned` (new) → `OnRecipientSigned` reactor | a real SE use-case produces incremental PAdES, then signals completion |

The SIGN-driven path is `OnRecipientSigned` (3b-i), fed in production by `SignForRecipientUseCase` (3b-ii) — precisely the v2 slot `OnSessionCompleted`'s docblock reserved.

> **Two claims in this paragraph did not survive the build, and the corrections are the interesting part.**
> - *"A cheap `signingMode` guard in each reactor selects exactly one completion path."* The guard moved onto the **command** (`CompletionDriver`) and into the **aggregate** (`Envelope::completesOn()`, a total `match`), because the aggregate is already loaded and locked there and reactors must stay dispatch-only. See slice 3b-ii and [ADR-0034](../adr/ADR-0034-sequential-incremental-pades.md) §3.
> - *"Chain ordering comes for free from the single ordered event-log consumer."* Only because `docker-compose.yml` happens to run exactly one `messenger:consume` — a property of a compose file, not of the design. Slice 3a replaced it with a compare-and-swap on the chain tip, so order is decided by who commits.

**Per-recipient signing assignments (the new domain concept — §5b of the design).** Recipient↔Document has **zero association today** (signing is envelope-wide; step closure counts recipient outcomes, never documents). Sequential mode needs a per-recipient **document-signing scope**: which documents a recipient signs, and whether each renders a visible mark.

- `SigningAssignment { documentId, renderMark: bool, position?: FieldPlacement }`, per recipient, on the Envelope aggregate (owns recipients + documents). *(As-designed sketch; the shipped shape carries a placement **list** and `renderMark` retired into it — §2, TASK-018.)*
- **Default when unspecified = *nothing assigned*** (revised — [ADR-0034](../adr/ADR-0034-sequential-incremental-pades.md) §6). The original design fanned an unassigned recipient out to *every document*; under `SEQUENTIAL_PADES` that failed **open** on a cryptographic act, so it was replaced by a pre-send completeness invariant — a recipient whose role signs must be assigned ≥1 document before the envelope can send. `SINGLE_SEAL` never assigns and is unaffected.
- **Backend stays generic** ("recipient R signs documents {…}, mark yes/no"); the **dashboard encodes the eCMR policy** (mirroring the existing generic-`SIGNER`-role / dashboard-derives-role-from-step split).
- **eCMR topology (from the two real Factor5 waybills):** an N-drop shipment = **1 conjunta PDF** (multi-page: global page + one page per destino) **+ N individual PDFs**. Cargador + transportista sign **every** document (visible marks). Each destinatario signs the **conjunta** (crypto layer; mark optional — the visual is rendered from the template's `{{Firma_Destinatario}}` placeholder, so `renderMark` may be false) **and their own drop PDF** (visible mark). So the assignment varies per (recipient, document) — hence the explicit model.

**Visual template layer (nuance, not this task's core).** The waybill PDFs carry named placeholders at the CONFORME boxes (`{{Firma_Cargador}}`, `{{Reservas_Transportista}}`, `{{Check_Conforme_Transportista}}`, …). This is a *visual rendering* concern (names/marks/reservations/checkbox → boxes) **separate** from our cryptographic PAdES layer, and it likely lives in the dashboard's template engine. `{{Reservas_*}}` is where [TASK-016](TASK-016-sign-with-reservations.md)'s reservation renders. Whose engine renders the visual — and whether our PAdES layer adds a visible widget or defers — is decided in the visible-mark slice, not the crypto foundation.

## 2. Build plan (slices on `feat/sequential-pades`)

**✅ Slice 1 — signing-mode config (DONE).** `SigningMode{SINGLE_SEAL|SEQUENTIAL_PADES}` in `Contract\Type` (edge-settable *and* SE-readable — so it can sit on the ACL-clean view SE consumes). Threaded into `Settings` (ctor / `defaultsFor`→`SINGLE_SEAL` / `equals`) + `Settings.orm.xml` + migration `Version20260708000003` (NOT NULL, transient default backfills existing rows; since consolidated into the `Version20260713*` baselines and no longer present as its own file) + DBAL write/read + read-repo hydrate. Settable at creation (`POST /api/v1/envelopes` `signing_mode`, optional→`SINGLE_SEAL`, invalid→422) via a `CreateEnvelope::draft` param. **Surfaced on GET** — added `signingMode` to `EnvelopeContextView` (the one settings field a cross-BC consumer needs) + presenter `signing_mode`. **Zero behaviour change at the default.**

**✅ Slice 2 — signing-assignment model (DONE).** `SigningAssignment{recipientId, documentId, renderMark}` in `Contract\Type` (SE reads it cross-BC) + `domain.signing_assignment` (migrations `Version20260709000001`, the shared trigger function, then `Version20260709000002`, the table — both since consolidated into the `Version20260713*` baselines and no longer present as their own files) + `Envelope::assignSigning()` + `AssignSigning` command/use-case/handler + `POST /api/v1/envelopes/{id}/recipients/{recipientId}/signing-assignments` → 204. Four decisions the design left open, resolved by the code:

- **No rows means nothing assigned** (revised — [ADR-0034](../adr/ADR-0034-sequential-incremental-pades.md) §6). `EnvelopeContextView::signingAssignmentsFor()` resolves exactly the stored rows: an empty set resolves to `[]`, not to "every document." The earlier virtual fan-out was removed because it failed open on a cryptographic act; a `SEQUENTIAL_PADES` envelope now cannot send with a signing recipient left unassigned, and `SignForRecipientUseCase` refuses a signatureless completion if one ever slips past. `SINGLE_SEAL` never assigns and stays byte-identical.
- **Assignments are append-only.** Two independent constraints force it: `DbalEnvelopeRepository`'s stated invariant that no child deletes exist, and the fact that Doctrine cannot swap an immutable VO on a managed entity without an INSERT onto an existing PK. Re-assigning a pair with the same mark is an idempotent no-op; with a *different* mark it raises `SigningAssignmentConflictException` (409) rather than silently dropping the change. Editing and un-assigning arrive with the DRAFT-PATCH surface (§4) — which is why §2's original "DRAFT-only update endpoint" is *not* built here.
- **Identity is the natural `(recipient_id, document_id)` pair** — a composite PK, so "one assignment per recipient-document" is the primary key rather than a constraint over a surrogate id.
- **It carries `tenant_id` + FORCE RLS from birth** (ADR-0017 §5), unlike its four sibling child tables, which are join-protected only. TASK-002 defers those because they need a backfill; a new table has none. Population is a `BEFORE INSERT` trigger (TASK-002 §4 Option A) so the domain and *both* persistence adapters never see the column. The trigger function `public.set_tenant_id_from_scope()` is shared substrate and gets **its own migration**, ahead of the table: TASK-002 attaches it to the four remaining child tables rather than authoring its own, and no table migration owns the lifecycle of a function its siblings depend on. PostgreSQL enforces the ordering — dropping the function while any trigger still references it is refused, so an out-of-order `down()` fails loudly instead of silently disarming tenant stamping.

Both repositories are wired: the ORM `DoctrineEnvelopeRepository` (the live container alias) and the DBAL twin (ADR-0018's head-to-head instrument), so flipping the alias does not silently lose assignments. `position` / field placement is deliberately absent — see §1's visual-template note; it joins this type, or doesn't, in the visible-mark slice.

**Slice 3 was split.** The original slice-3 spec bundled two independent risks: rewiring *which event completes a recipient* (touches both live completion paths, `SigningLoopTest`, and `EnvelopeVerticalSliceTest`) and *producing real cryptography* (touches DSS, the object store, and an async scenario test whose failure modes are timing, not logic). Landing them together means that when the suite goes red, nothing tells you which half is wrong. They are now 3a / 3b-i / 3b-ii, each independently green and committable.

**✅ Slice 3a — seal the tip, guarded by compare-and-swap (DONE).** `DocumentSealer` reads the document's chain **tip** instead of `originalStorageKey`, so the company seal wraps whatever signatures have accumulated. `DocumentView` gained `tipStorageKey` + `tipArtifactId`, projected by a correlated subquery mirroring the original one with the sort reversed (head and foot of the same append-only chain, in the query the seal loop already runs — no N+1). `appendDocumentArtifact` gained an optional **`expectedTipId` compare-and-swap**, and `Document::appendArtifact` enforces it.

- **Why CAS.** The document row lock is taken *inside* the append — after the caller read the tip and spent seconds in DSS. Two recipients of the same step (all-required and concurrent, per [TASK-016](TASK-016-sign-with-reservations.md)) signing the same document would both read tip *N*, both sign over *N*, and both append; the later artifact's bytes omit the earlier signature and nothing detects it. §D2's "chain ordering comes for free from the single ordered event-log consumer" is true only because `docker-compose.yml` happens to run exactly one `messenger:consume`. That is a property of a compose file, not of the design. With CAS, order is decided by who commits, and the loser re-reads the tip and re-signs.
- **`ArtifactChainConflictException` lives in `Contract/Exception`, not `Domain/Exception`** — the caller who must catch and retry it is SignatureExecution, whose layer may not import Envelope's `Domain` and so could not catch a Domain exception by type (ADR-0004: the ACL spans the error channel).
- **`MockSignUseCase` was dishonest and this exposed it.** It appended a SIGN artifact naming `mock://signed/…`, a key holding no bytes — invisible only while the sealer read the original and ignored the tip. It now copies the tip's bytes into the WORM `signed` zone, hashes them, and compare-and-swaps on the tip it copied. Only the cryptography is still mocked.
- **`SINGLE_SEAL` is byte-for-byte unchanged**: with no SIGN artifacts the tip *is* the original.

**✅ Slice 3b-i — the completion topology, no cryptography (DONE).** Done first because it is the half that can break the two existing end-to-end tests: isolating it means a red suite implicates the topology and never DSS.

- New per-recipient event `RecipientSigned` (SE `Contract/Event/`), carrying `reservations` from birth so the 3b-ii thread has somewhere to land. One file registered it — `RegisterDomainEventsPass` globs `**/Contract/Event/*.php` and reads `EVENT_TYPE` by reflection; `SignatureExecution/Contract/` is excluded from the DI resource scan, so no `services.yaml` edit. It streams under the **envelope** (overrides `streamKey()`) exactly as `SessionCompleted` and `DocumentSigned` do. **No infra change:** the broker binding is the wildcard `App.SignatureExecution.Event.#` → `queue.signatureexecution.events`, and the worker consumes all three event queues, so a new SE event routes itself. (Handlers live wherever the reactor lives — the binding is by the event's *origin* BC, not its consumer's.)
- Envelope `Application/Subscriber/OnRecipientSigned` + `Infrastructure/Messenger/Subscriber/OnRecipientSignedHandler` (naming enforced by `SubscriberConventionsRule`; `_instanceof` auto-tags the handler, no DI entry). It dispatches `RecordRecipientCompletion`, carrying `reservations`.
- **`OnDocumentSigned` + its handler are deleted.** Both it and `OnSessionCompleted` dispatched `RecordRecipientCompletion`, ungated — safe only because `MockSign` is test-only (`new MockSign(` appears nowhere in `src/`) and `Recipient::markCompleted` is idempotent. Once a recipient signs N documents a per-document driver fires N times. `DocumentSigned` is now the audit fact it always should have been: still appended, **no reactor** (`event.bus` sets `allow_no_handlers: true`), and the Evidence & Audit projector is its consumer.
- `MockSignUseCase` emits `DocumentSigned` (audit) **then** `RecipientSigned` (completion) in one transaction — a faithful mock rather than a divergent one, and the completion follows the artifact it attests to in log order.
- `EnvelopeVerticalSliceTest` now pins the topology: the `DOCUMENT_SIGNED → RECIPIENT_SIGNED → RECIPIENT_COMPLETED` subsequence, and **exactly one `RECIPIENT_COMPLETED` per recipient** — the property `DocumentSigned` cannot carry once a recipient signs more than one document. `SigningLoopTest` stayed green untouched (it drives the `SINGLE_SEAL` path).
- **Verified by falsification, not just by green.** Suppressing the `RecipientSigned` append turns both end-to-end tests red (envelope stalls at `SENT`), which is what proves completion actually rides the new event rather than merely coexisting with it.
- **Doc pointers repointed** (they would 404 or lie): ADR-0002's reference reactor/adapter pair, ADR-0004's translation-seam list, `docs/ddd/signature-execution-domain-model.md`'s cross-BC-seam row. ADR-0024's context section and ADR-0027's rationale still name `OnDocumentSigned` **and are left alone** — they are dated records of a decision's moment (ADR-0027 still says "outbox", retired long since), not live claims.
- **No behaviour change end-to-end.** Same completions, same orderings, different event carrying them.

**✅ Slice 3b-ii — the real crypto path (DONE).** SE's `OnSessionCompleted` reactor → `SignForRecipient` → `SignForRecipientUseCase`, which loops `EnvelopeContextView::signingAssignmentsFor(R)` and, per assigned document, reads the tip bytes, drives an incremental PAdES through `DssClientInterface::seal`, stores to the `signed` zone, and appends a SIGN artifact via `ProducedBy::sign(ExecutionRef)` with the CAS token from `DocumentView::tipArtifactId` — catching `ArtifactChainConflictException`, re-reading the context, re-signing (3 attempts). One `DocumentSigned` per document (audit), then one `RecipientSigned(R)`. Decision record: **[ADR-0034](../adr/ADR-0034-sequential-incremental-pades.md)**.

- **The mode gate moved.** §2's plan put it in the reactors, reading `signingMode` through a lean `EnvelopeReadRepository` method. It sits instead on the **command**: `RecordRecipientCompletion` carries a `CompletionDriver{CONSENT|SIGNATURE}`, and `Envelope::completesOn()` declines the driver its mode did not elect — where the aggregate is *already loaded and row-locked*, so it costs no query, keeps reactors dispatch-only (ADR-0002), and makes "one completion path per mode" an aggregate invariant over a total `match` instead of a rule each future reactor must remember. SE's own gate is free: its use-case reads the context regardless. `CompletionDriver` lives in `Domain/ValueObject` (never edge-set, never read cross-BC), beside `TargetSignatureProfile`.
- **`DocumentSealer` → `DocumentSigner`,** with `seal()` and `sign()` over one private `apply()`. The two acts differ *only* in `ProducedBy` provenance; a class named "Sealer" appending SIGN artifacts is the multi-shape-per-concept smell. Keeping one byte-path is what makes `upload → sign₁ → … → seal` a single append-only structure.
- **`reservations` threaded** (`SessionCompleted` → `SignForRecipient` → `RecipientSigned` → `RecordRecipientCompletion`), so the eCMR attest-with-exception text (TASK-016) survives the SE hop. Asserted end-to-end.
- **`renderMark` is carried but NOT rendered** — `SignatureImage` needs page + coordinates and slice 2 stored no placement, so `sign()` is invisible regardless of the flag, and says so. See §4.
- **`MockSign` is now a mock of `SignForRecipientUseCase`**, so a `MockSign`-driven envelope must be `SEQUENTIAL_PADES` (it triggers the signature-driven completion). `EnvelopeVerticalSliceTest` + `EnvelopeSealLoopTest` were switched accordingly; `SigningLoopTest` keeps the consent-driven `SINGLE_SEAL` path covered.
- The seal loop needed no change: 3a already points the sealer at the tip.

**✅ Slice 4 — resilience (DONE; pairs with the infra `feat/sequential-pades` broker-topology commit — the two merge together).** Retry with backoff + a dead-letter queue, so a transient DSS outage no longer hard-stalls an envelope. **Retry was not merely unconfigured — it was broken three independent ways, each silent**, and the config alone would have papered over all three:

- **The `delays` exchange did not exist.** Under `auto_setup: false` Symfony still *binds* its per-delay queues to `delays` (their names embed the routing key + delay, so they cannot be pre-declared) but does **not** declare the exchange. Every delayed redelivery died on a 404 at publish. Declared in infra (`definitions.json`); *not* `f5sign.delayed`, which is the `x-delayed-message` plugin Messenger cannot drive.
- **`SelfSerializingMessageSerializer::decode()` dropped `RedeliveryStamp`.** The retry counter reset to 0 on every redelivery, so `max_retries` never tripped and nothing ever reached a dead-letter queue: a permanently-failing fact would retry forever. Now an `X-Redelivery-Count` header, an explicit carrier like tenant.
- **`decode()` dropped `AmqpStamp`.** A retried fact was re-published with an *empty* routing key, matched no binding on the `f5sign.events` topic exchange, and was swallowed by the alternate exchange into `queue.events.unroutable`. The key is now re-derived from the event class on decode, exactly as `EventRelay` derives it on the way out.

All three are pinned by `EventBrokerRetryDeliveryTest` against the live broker, and each was **falsified** (delete the exchange / revert the stamp → red).

- `retry_strategy`: 4 retries, 2s → 6s → 18s → 54s (capped 60s) ≈ 2.3 min of tolerated outage. `DssHttpAdapter` already retries the HTTP call itself (ADR-0012), so reaching the transport retry means the *service* is down, not a request.
- `failure_transport: failed` → `f5sign.failed` fanout → `queue.failed`. Replayable with `messenger:failed:retry`. It keeps Messenger's **default PHP serializer** (its envelope carries `ErrorDetailsStamp` etc., which the plain-JSON codec cannot express; nothing but an operator consumes it). AMQP receivers are not listable, so `messenger:failed:show` does not work — deliberate: a Doctrine failure transport would copy tenant-scoped payloads into a table with no RLS (ADR-0017), a worse trade.
- **No idempotency machinery was needed**, which is the slice's one pleasant surprise. The whole signing act runs in a single `doctrine_transaction` on the command bus, so a DSS death on document 2 rolls back document 1's artifact *and* its `DocumentSigned`. A retry re-runs from a clean slate. `FailedSignatureRollbackTest` checks exactly that — including that DSS really signed once before dying, so the rollback undid something. Only the object-store bytes are orphaned (unreferenced, unreachable).

## 3. The completion wrinkle (why `RecipientSigned`, not per-doc `DocumentSigned`)

A recipient now signs **N** documents (cargador signs all), so "signed" must gate on **all N SIGN artifacts landing**, not one. The tests-only `MockSign` path was per-single-document. Resolution: the SE use-case, on `SessionCompleted(R)`, produces all of R's SIGN artifacts (each may emit a per-document `DocumentSigned` for audit), then emits **one** per-recipient `RecipientSigned(R)` that drives `RecordRecipientCompletion` once. Step-closure stays recipient-counted (unchanged); "signed" now means "all assigned documents signed."

Wiring it through would flip every seal to B-LT and break sealing. Belongs in the eIDAS-validated phase (`/eidas-compliance`).

Real personal-key non-repudiation; a large separate initiative. Server-sign-as-signer is reversible to this on the same substrate.
- **Visual template rendering** (placeholder → names/marks/reservations/checkbox into the CONFORME boxes) — a dashboard-template concern; decide in the visible-mark slice. Three constraints already known, from the Factor5 dashboard prototype (OFFREPO, see the header note): placement is **per `(role, page)` and is a list**, so a single `position` field on `SigningAssignment` would be the wrong shape; PAdES ties **one visible widget to one signature**, which is why the prototype carries a strategy switch between *one signature per box* and *plain image stamps plus a single signature*; and the coordinates are PDF points measured from the **top-left**, `originY` increasing *downward* — DSS's convention, the opposite of PDF user space. (Earlier revisions of this note said bottom-left. That was wrong, and it was silent: it mirrors every mark vertically. Verified against the live DSS — `originY: 50` on a 792pt page yields `/Rect [40 702 140 742]`; see `SignatureImage`'s docblock.) They are **measured off the rendered Twig template**, so they are template-coupled and must be recomputed whenever the template moves. Two DSS gotchas worth keeping: never set `textWrapping` on `imageParameters.textParameters` — DSS then scales the font to the box width and throws *"signature field box is too small"*; and one `imageParameters` block means **one visible widget per signature**, so N marks for one signer on one document means N incremental signatures.
- **DRAFT-PATCH update endpoints** for `signingMode` + assignments ("maybe" per the design discussion) — build when after-the-fact edits are needed.
- **Decline-to-participate** (per-recipient decline-disposition that reopens inv 26) — separate from attest-with-reservations ([TASK-016](TASK-016-sign-with-reservations.md), done); only if a destinatario can refuse outright.

## 5. Verification

**⚑ The load-bearing assumption is no longer an assumption (probed against the live `eu-dss`, 2026-07-09).** D1 rests on "feed the tip bytes back through `DssClientInterface::seal` and you get an incremental update that preserves prior signatures." Measured, not inferred:

- Signing the same PDF three times in succession yields **prefix-preserving** growth — `s3` literally begins with `s2`, which begins with `s1` — and four `%%EOF` markers, one per PDF revision. That is a true incremental update, not a rewrite.
- The DSS validator (`POST /services/rest/validation/validateSignature`) reports **three distinct signatures**, each with its own ByteRange (`[0,731,38621,770]` → `[0,39782,77672,812]` → full document), all cryptographically **intact**.
- Flipping **one byte inside revision 1** turns *all three* to `TOTAL_FAILED / HASH_FAILURE` ("The reference data object is not intact!"). The chain-of-custody property this task claims — tampering with an earlier leg invalidates every later signature — is real.
- No DSS change is needed: `DssPayloadMapper`/`DssHttpAdapter` sign whatever bytes `SignRequest` carries, and `signatureLevel` is already a pass-through. The only thing pinning the seal to the original was `DocumentSealer`, fixed in 3a.

**⚑ Test assertions must check integrity, never validity.** The dev keystore is **self-signed**, so every signature validates as `INDETERMINATE / NO_CERTIFICATE_CHAIN_FOUND` — a *trust* verdict, not an integrity one. Asserting "valid" will fail for a reason unrelated to the code, and will keep failing until Factor5 procures the certificate (the same gate as `padesTargetProfile`, §4). Assert on the absence of `HASH_FAILURE` / "not intact", or on the signature count and ByteRanges.

- `make qa` green at each slice. Migrations apply + reverse on a scratch DB. **Stop the workers first** (`make worker-down`): a running `relay`/`worker` shares the broker with `EventLogBrokerRoundTripTest` and makes it fail ~1 run in 3.
- **Slice 1 (done):** read-repo round-trip (default `SINGLE_SEAL` + non-default `SEQUENTIAL_PADES` persist/rehydrate); HTTP create edge (POST `signing_mode` → GET `signing_mode`; omitted → `SINGLE_SEAL`; invalid → 422); live curl on `:8000`.

### Driving an envelope end to end (dev stack, over HTTP)

Proven working on 2026-07-09: `COMPLETED` in ~6s, chain `UPLOAD → SIGN → SEAL`, the recipient's visible mark at exactly the authored rect.

```
make up                     # from ../f5sign-infra
make worker-up              # ← the async pipeline is OFF by default. Without it nothing completes.
docker compose exec php-fpm php bin/console cache:clear   # ← see the trap below

POST /api/v1/envelopes                                        {"signing_mode":"SEQUENTIAL_PADES", …}
POST /api/v1/envelopes/{id}/documents                         → documentId
POST /api/v1/envelopes/{id}/documents/{docId}/content         multipart, field name `file`
POST /api/v1/envelopes/{id}/steps                             {"ordinal":1}
POST /api/v1/envelopes/{id}/recipients                        {"step_ordinal":1,"role":"SIGNER",…}
POST /api/v1/envelopes/{id}/recipients/{rid}/signing-assignments
                                {"document_id":"…","placements":[{"page":1,"origin_x":40,"origin_y":50,"width":220,"height":40}]}
POST /api/v1/envelopes/{id}/send
POST /api/v1/signing-tokens                                   {"envelope_id":"…","recipient_id":"…"} → bearer token
POST /api/v1/signing/session      Authorization: Bearer <token>
POST /api/v1/signing/commit       Authorization: Bearer <token>   {"consent":true,"reservations":"…"}
GET  /api/v1/envelopes/{id}                                   poll until "COMPLETED" (async)
GET  /api/v1/envelopes/{id}/documents/{docId}/sealed          the signed bytes
```

Sender calls carry `Authorization: Bearer <api-key>` + `F5Sign-Declared-Subject` ([ADR-0047](../adr/ADR-0047-qualified-actor.md), [ADR-0048](../adr/ADR-0048-route-declared-authentication-seam.md)); the tenant comes from the verified credential, not from a header the caller supplies. *(Until the 2026-08-06 cutover these were the `X-Tenant-Id` + `X-Acting-User-Id` stub headers of ADR-0022.)* The recipient calls carry only the bearer token (ADR-0028). `origin_y` measures **down from the page's top edge**; on a 792pt page, `origin_y: 50` renders at `/Rect [40 702 260 742]`.

**Two operational traps, both of which look exactly like a code bug.**

1. **`make worker-up`.** The worker + relay sit behind a compose profile and do **not** start with `make up`. The whole sequential flow is async, so without them a committed signature leaves the envelope stuck at `SENT` forever, with nothing in the logs because nothing is consuming.
2. **`cache:clear` the *dev* environment after touching a Doctrine mapping or `messenger.yaml`.** `var/cache/dev` is bind-mounted and shared with the worker, and it is **not** rebuilt by `make qa` (which runs in `test`). A stale compiled container makes the worker silently run yesterday's config: it hydrated `Settings` from a `ClassMetadata` that predated `signingMode` and died with *"Typed property Settings::$signingMode must not be accessed before initialization"*, while also ignoring the configured `retry_strategy` and `failure_transport` — so the poisoned message was dropped instead of parked. Every symptom pointed at slices 1 and 4; the cause was a cache. `EnvelopeSettingsHydrationTest` now guards the hydration half of it.

Four things that will otherwise cost an hour to rediscover:

1. **Persistence is DBAL-only** — [ADR-0018](../adr/ADR-0018-dbal-only-persistence.md) is Accepted/realized; the ORM adapter + `.orm.xml` are **gone** and `DbalEnvelopeRepository` is the single live adapter. *(During this branch's build the ORM adapter was still the live alias and the DBAL one an A/B twin; that flipped when ADR-0018 shipped — a change to aggregate persistence now lands in one place.)*
2. **A deptrac allowlist is not the architecture.** `deptrac.yaml`'s header and ADR-0004 state the rule; the ruleset merely enforces it, and it had drifted. Read the rule before concluding a dependency is forbidden.
3. **A `Contract/Type` value object needs a private constructor and a `from*` factory** (`ValueObjectShapeRule`). `DocumentArtifact`'s public constructor is *baselined* as a tracked finding — don't copy it, and don't extend `phpstan-baseline.neon` without categorizing the finding in the design repo.
4. **Two reactors dispatch `RecordRecipientCompletion`** — `OnSessionCompleted` (consent-driven, `SINGLE_SEAL`) and `OnRecipientSigned` (artifact-driven, `SEQUENTIAL_PADES`) — and the mode gate **is now enforced** (slice 3b-ii): it moved off the reactors onto the **command** (`RecordRecipientCompletion` carries a `CompletionDriver`) and into the aggregate (`Envelope::completesOn()`, a total `match`), so an envelope completes on exactly its mode's driver. Reactors stay dispatch-only (ADR-0002).
