⛑ **2026-09-29 — what TASK-050 changed in this record** (merged on the same branch at `f48b14e2`; the text below is left as written, and these are the rows it made stale). See [TASK-050 signer](TASK-050-signer-step-policy-and-what-a-recipient-reads.md) for the current contract.

- **`DECLINE_NOT_OFFERED_IN_QUORUM_STEP` is retired** (`8f42995d`): out of the `ProblemCode` enum and the decline route; a decline inside an `AT_LEAST` step answers 200. Every "still emitted / do not remove yet" below was true on 2026-09-28 and is not now.
- **`REVOKED` no longer means "the envelope ended without agreement".** `SessionStatus::outcomeAtTheGate()` now lets a revoked session whose leg the envelope closed read the envelope's name for that leg (`RELEASED` or `DECLINED`), and `/auth` gains `envelope_outcome` (`AGREED`/`NOT_AGREED`) for how the envelope ended. A released signer reads `RELEASED` before and after the revocation lands. The "`REVOKED` or `RELEASED` depending on…" reading below is superseded.
- **`SESSION_CLOSED` is reworded** (`aca35852`): a released leg closed the session, not necessarily the sender.
- **Informational members no longer hold their step**, and their commit is refused `COMMIT_NOT_OFFERED_TO_ROLE` (`1cc5ef0e`); their session survives a release or a void (`480faab9`).
- **The auth submit now answers `LEG_CLOSED` too** (`fb875674`): when a step deadline releases the leg in the instant before the pass is recorded. The bullet below saying auth submit does not distinguish it was true when written. Session open also re-checks the gate under the recipient row's lock.
- **An act past its step's deadline, before the sweep, answers `LEG_CLOSED`** (`eb686c5f`).
- **`ENVELOPE_NO_LONGER_LIVE` no longer tells the client to say "cancelled"** (`70a0e89d`): an envelope also closes agreed without a released member.

## Changed since the provisional handoff

The provisional draft (`notes/adr-0073-provisional-handoffs/handoff-signer-adr0073.md`) was written against ADR-0073's text alone, before any of this was code. Verified against the actual tree, here is everything that differs:

- **`RELEASED` IS published, on one route only, and this corrects an earlier pass of this same handoff.** `GET /api/v1/signing/session/auth`'s `outcome` gains a fourth member, `'RELEASED'`, answering the draft's open question directly: the envelope closed while this recipient's part was still open, and released them — they did nothing, and nothing more is asked of them. It is published **even when they never opened a session**, which is the whole reason it exists: `SessionStatus` alone cannot answer this (a released leg may have no session row at all, or a live one the revocation hasn't reached yet), so a new static, `SessionStatus::outcomeAtTheGate(?SessionStatus $status, bool $recipientPassesTheGate, ?string $closedLeg)`, layers the envelope's own outcome for the closed leg underneath the session's: the session's `terminalOutcome()` first, then `null` if the gate still passes, then — reading the closed leg — `RELEASED` for a release, `DECLINED` for a decline, `REVOKED` for anything else (a void, a veto, an ending nobody decided). `SessionStatus::RELEASED_OUTCOME` is a string constant (`'RELEASED'`), **not a `SessionStatus` case** — no session is ever released, only a leg. ⚠ A released member who can *still* read — an informational role, or anyone who signed — is let back in instead and never sees `RELEASED`: the gate passes for them, so the session's own answer (or `null`) wins.
- **`POST /api/v1/signing/session`'s `status` is unaffected — confirmed still just the five values, no `RELEASED`.** A recipient whose gate is shut there is still refused outright (409 `LEG_CLOSED` or `ENVELOPE_NO_LONGER_LIVE`, see below) rather than being let through with a `RELEASED` status; `RELEASED` is an *auth-descriptor* concept only, for a route that answers 200 pre-credential.
- **A new 409 code exists on session open that the draft did not know about: `LEG_CLOSED`.** `POST /api/v1/signing/session` now distinguishes two cases the draft's §4 question 4 asked about as one: a recipient whose leg the envelope released **while the envelope is still open** (another leg is still live) gets `LEG_CLOSED`; a recipient whose leg closed **because the whole envelope ended** gets `ENVELOPE_NO_LONGER_LIVE`, as before. It is documented on that route's published 409, beside `ENVELOPE_NO_LONGER_LIVE`, `RECIPIENT_SIGNS_ELSEWHERE` and `STEP_NOT_ACTIVE`.
- **`LEG_CLOSED` also reaches the commit and the decline** (`POST /signing/commit`, `POST /signing/decline`, and the integrators' delegated commit). Every act is admitted on the envelope under its lock, and the admission refuses a leg that is already admitted or released while the envelope is still open; a closed envelope answers `ENVELOPE_NO_LONGER_LIVE` ahead of it, as on session open. It can arrive before the session itself has been closed, which is why it is not `SESSION_CLOSED`. Documented on both routes' published 409.
- **`ENVELOPE_BUSY` (503, `Retry-After: 2`) reaches two signer routes, not four — and this corrects an earlier pass of this same handoff.** The gate's opening write (`recordOpening()`, in `EnvelopeCommandAdapter`) no longer refuses on a recipient-row lock timeout: it now swallows `EnvelopeLockTimeoutException` and simply records nothing, so session open and the access-gate answer (`POST /signing/session`, `POST /signing/session/auth`) never produce this 503 — the relay-borne twin of the opening fact lands later if the envelope is still open. Only commit and decline (`POST /signing/commit`, `POST /signing/decline`) still wait on the envelope's root lock to admit the act, and can still answer it. The machine-key delegated commit can too, but that route is the integrator handoff's concern, not this one.
- **The OTP-send and auth-submit routes do NOT distinguish `LEG_CLOSED` from `ENVELOPE_NO_LONGER_LIVE`.** Both `POST /signing/session/auth/otp/send` and the auth response submission answer `ENVELOPE_NO_LONGER_LIVE` for a gate failure of either shape — confirmed in `IssueAuthChallengeUseCase` and `SubmitAuthResponseUseCase`, both of which pass the gate rule's answer (`$auth->gatePasses`) as `envelopeIsAlive` and refuse under that one name. Session open, commit and decline tell the two apart; OTP send and auth submit do not.
- **Session renewal now asks the gate rule too, and this is new.** `POST /signing/session/renew` used to check only the credential's validity. It now also reads whether this recipient can still pass the gate, and answers a bare `401` (no distinguishing code — same shape as every other refusal on that route) when they cannot. This did not exist in the provisional draft at all, because it is part of the work landed after `8cd3424a` on this branch.
- **`SEAL_PENDING` on `GET /signing/session` now covers both outcomes**, not only a voided envelope as the draft (correctly, per the ADR text) anticipated. Confirmed in code: `readsWaitForTheSeal()` is re-keyed on "closed and not `COMPLETED`" rather than on the voided status, which no longer exists.
- **The decliner's read narrowing is confirmed exactly as drafted, with the code now real.** Since `COMPLETED` (either outcome), only a recipient who signed (an admitted approval counts) or who reads as informational is served the sealed document; a decliner, or any other released member, gets `ENVELOPE_NO_LONGER_LIVE` instead of the 200-with-PDF that TASK-046 gave them under `VOIDED`.
- **`DECLINE_NOT_OFFERED_IN_QUORUM_STEP` is still emitted — confirmed, not retired in this branch.** It is still in the published `ProblemCode` enum (`config/packages/nelmio_api_doc.yaml`) and is still the referenced refusal on `POST /api/v1/signing/decline` and in `SigningSessionStateException`. Its retirement is TASK-050's, not this one's. Do not remove the `useSignerNavigation.ts` branch for it yet.
- **Nothing the draft said about `envelopeStatus`/`recipientStatus`-shaped mapping applies to the signer** — that section of the sibling integrator draft is about `dashboard-sf`, not this repo; the draft's own signer document did not claim it, so there is no correction here, only a note that the two drafts should not be conflated.

## What changed in the contract

- **`POST /api/v1/signing/session`** (`status` field): the same five values as before (`AUTH_PASSED`, `AUTH_PENDING`, `COMPLETED`, `DECLINED`, `REVOKED`) — no new member — but **`REVOKED` is now reachable by more than a sender's void**: a blocking recipient's decline, a veto, or an ending nobody decided (`MINIMUM_UNREACHABLE`, `STEP_DEADLINE_MISSED`, `MEMBER_NOT_REACHED`) all close the envelope the same way, and every one of those produces `REVOKED` here too. New 409 `LEG_CLOSED` on this route (see above).
- **`GET /api/v1/signing/session/auth`** (`outcome` field): gains a fourth member, **`RELEASED`** — the envelope closed while this recipient's part was still open, and released them; published even when no session was ever opened for them, or the revocation fact has not reached their session row yet (`SessionStatus::outcomeAtTheGate()`). `REVOKED` stays reachable for every other way a leg closes without the recipient's act (a void, a veto, an ending nobody decided). A released member who can still read (an informational role, or anyone who signed) is let back in instead and never sees `RELEASED` or `REVOKED` here.
- **`GET /api/v1/signing/session`**: `SEAL_PENDING` (409) generalizes from "voided envelope, signer or decliner" to "any closed-and-not-`COMPLETED` envelope, for a recipient who signed or reads as informational." `ENVELOPE_NO_LONGER_LIVE` (409) now also covers a decliner or a released non-informational member reading after `COMPLETED` — previously a decliner read the sealed document there (TASK-046); now they are refused.
- **`POST /api/v1/signing/session/renew`**: new — a bare 401 when the recipient can no longer pass the gate, even if the presented credential is otherwise valid.
- Committing (`POST /api/v1/signing/commit` and the delegated-commit route) still answers `STEP_NOT_ACTIVE` (409) **before** `FIELD_VALUES_INVALID` (422) — unchanged from TASK-044, reconfirmed in the current `#[OA\*]` text.
- **`POST /api/v1/signing/commit`** and **`POST /api/v1/signing/decline`**: new 409 `LEG_CLOSED` (see above). `DECLINE_NOT_OFFERED_IN_QUORUM_STEP` stays on the decline.
- **New 503 `ENVELOPE_BUSY`** (`Retry-After: 2`) on `POST /signing/commit` and `POST /signing/decline` only — not on session open or auth submit (see above).

## What the frontend has to do

1. **Add a `LEG_CLOSED` branch on session open, commit and decline**, distinct from `ENVELOPE_NO_LONGER_LIVE`. Both should probably land on a similar "nothing left to do here" screen, but they are different facts: `LEG_CLOSED` means this recipient's own turn is over while the document is still moving for someone else; `ENVELOPE_NO_LONGER_LIVE` means the whole thing ended.
2. **Add a `RELEASED` branch on `GET /signing/session/auth`'s `outcome`.** It is a distinct, published value now — a recipient whose part simply never got acted on before the envelope closed some other way, as opposed to `REVOKED`'s "the whole thing ended in a way that admits no more acts from anyone." A generic "nothing left to do" screen can still cover both, but the two are no longer the same value on the wire and treating an unhandled `RELEASED` as an unknown/default case would be wrong now that it is named.
3. **Stop assuming `REVOKED` always means "the sender cancelled."** It is reachable now by a blocking recipient's own decline or veto, or by nobody being reachable in time. If your `legRevoked`-style copy names the sender as the actor, it will sometimes be wrong. Nothing on the wire distinguishes those causes further — `REVOKED` stays one value however the envelope ended without agreement — so if the copy has to change, it needs a more neutral wording ("there is nothing left to sign here") rather than a new field to read, because none is published on this route.
4. **Confirm the decliner's screen never surfaces a download.** If `declined.vue`-equivalent code offers any document link, it must go: the backend refuses it now with `ENVELOPE_NO_LONGER_LIVE`.
5. ~~**Do not remove the `DECLINE_NOT_OFFERED_IN_QUORUM_STEP` branch** in `useSignerNavigation.ts` or wherever it is handled — confirmed still live.~~ ⛑ **2026-09-29**: retired by TASK-050 (`8f42995d`); the TASK-050 signer handoff says what to remove.
6. **Treat `ENVELOPE_BUSY` (503) as retryable** on `POST /signing/commit` and `POST /signing/decline`: wait `Retry-After` seconds and retry, rather than showing the signer a failure of their action.
7. **Handle the renewal's bare 401** the same way you handle any other renewal failure (send the signer back through their invitation link) — there is no new code to branch on, only a fact that renewal can now fail for a reason unrelated to the credential's own expiry.

## How to verify it from the signer

Against the deployment that eventually serves this: open a two-signer envelope where each signer is a separate blocking recipient in its own step. Have the first signer sign, then have the sender void the envelope (or have a third recipient veto, once TASK-050 lands) before the second signer acts — the second signer's session should read `REVOKED` on `POST /signing/session`, and either `REVOKED` or `RELEASED` on `GET /signing/session/auth` depending on whether the sender's void produced a decision (`REVOKED`) or simply released a member whose step never got its turn (`RELEASED`) — and should get `ENVELOPE_NO_LONGER_LIVE` rather than a sealed copy once the envelope reaches `COMPLETED`. The first signer should meet `SEAL_PENDING` until the seal lands, then read their signed copy. A recipient who declines should never see a document link on their declined screen, before or after the envelope closes. Add a case with an informational recipient (VIEWER/REVIEWER/EDITOR) whose step never activated before the void: their `GET /signing/session/auth` should read `null`/proceed (let back in), never `RELEASED`.
